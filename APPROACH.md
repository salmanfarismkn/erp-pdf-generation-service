## 1. Initial Understanding

My initial reading was that this was not primarily a “turn JSON into a PDF” problem. Rendering a single invoice from HTML is relatively straightforward; the harder part is making the service predictable when many requests arrive together, documents are large, bulk jobs run for minutes, clients have unreliable connections, and source data changes while a batch is running.

The main constraints I identified from the brief were:

- A single-document request should start downloading within five seconds.
- A bulk request can contain up to 100 documents and needs progress tracking and a ZIP download.
- The service should tolerate about 1,000 single-document requests per minute at peak, plus 5–10 bulk requests per minute.
- Rendering takes approximately 2–3 seconds and can temporarily use around 400 MB of memory per render.
- Some purchase orders have 500+ line items and have caused memory pressure.
- Bulk downloads can be interrupted by unreliable internet connections.
- Every document in a batch must reflect one submission-time snapshot, not a mixture of old and new ERP values.
- The service needs evidence that generated files have not changed after the archive was created.
- The monthly infrastructure budget target is under ₹12,500.

The hardest parts are therefore admission control and resource sizing, durable asynchronous work, idempotency and recovery, snapshot consistency, reliable downloads, and tamper evidence. A working PDF response is necessary but not sufficient evidence that these concerns are solved.

## 2. Assumptions & Clarifying Questions

### Assumptions used for this implementation

1. The existing ERP remains the system of record. The PDF service receives a JSON representation of an invoice or purchase order rather than querying and owning the ERP's business data.
2. The JSON payload persisted with a bulk job is the authoritative snapshot for that job. Rendering must not fetch the invoice again later.
3. A batch accepts 1–100 documents. The service can report per-document failures and produce a manifest describing successful and failed documents.
4. PDF rendering is CPU- and memory-intensive. Rendering concurrency must be explicitly bounded rather than increasing without limit.
5. Redis/BullMQ is used for asynchronous bulk execution; PostgreSQL remains the durable record of jobs and the transactional outbox.
6. Generated ZIP files are stored in configured local storage for the current working model. A multi-instance deployment would need shared durable object storage or a storage abstraction with equivalent semantics.
7. The API uses an API key and tenant header for this internal-service model. This is not a replacement for end-user identity, role-based authorization, or a full service-to-service identity system.
8. The load figures are treated as peak arrival rates, not as proven measured throughput.
9. The local tests described below are evidence for the tested paths only; they do not prove that the target peak load or a cloud deployment is supported.

### Questions I would ask before production implementation

- Does “1,000 single requests/minute” include documents submitted inside bulk requests, or are the 5–10 bulk requests/minute additional traffic?
- Is the five-second single-document SLO measured to response headers, first PDF byte, or complete download? What percentile is required (for example, p95)?
- Are requests synchronous until a PDF is ready, or can the primary ERP accept a job ID and poll later?
- What are the maximum JSON body size, line-item count, image/logo size, and permitted fonts?
- How long must PDFs and ZIPs be retained? Are there legal retention, deletion, residency, or audit requirements?
- Can invoices contain personal or financial information that requires encryption at rest, restricted access, or redaction in logs?
- What is the expected distribution of document sizes, cache hit rate, peak duration, and daily traffic?
- Does the upstream ERP provide a consistent database snapshot when it constructs a batch payload?
- What is the required recovery-time objective after a worker or host failure?
- Is multi-AZ availability required, and what is the acceptable cost if it is?
- Is the ₹12,500/month cap inclusive of the existing ERP/database/Redis infrastructure, tax, backups, network egress, and observability?
- What should happen if some documents in a batch fail: fail the whole batch, or return a partial archive with an explicit failure report?

## 3. Capacity Planning & Math

### Arrival rate

The peak single-document rate is:

\[
\lambda = \frac{1{,}000\ \text{requests}}{60\ \text{seconds}}
= 16.67\ \text{requests/second}
\]

For a render time of 2–3 seconds, Little's Law gives the approximate number of simultaneously active renders needed just to keep up with the arrival rate:

\[
L = \lambda W
\]

- At 2 seconds: \(16.67 \times 2 \approx 33.3\) active renders.
- At 3 seconds: \(16.67 \times 3 \approx 50\) active renders.

At 400 MB of temporary memory per active render, renderer memory alone would be approximately:

- \(33.3 \times 400 \approx 13.3\) GB.
- \(50 \times 400 = 20\) GB.

That excludes the OS, API process, Redis/PostgreSQL clients, Chromium baseline memory, file buffers, and safety headroom. Therefore, a single 16 GB host cannot safely sustain this peak if the 400 MB/render estimate is representative and all requests require a fresh render. A queue protects the host from overload, but it does not create capacity: if arrivals persist above service capacity, queue delay grows.

A single renderer at 2–3 seconds/render has a theoretical upper bound of about 20–30 PDFs/minute before overhead. The local load tests reported higher throughput (3.68 successful requests/second in one 40-request test), showing that the tested sample/template/environment did not exhibit the same 2–3-second render cost. I would not use that short local result to override the conservative requirement supplied in the problem statement. Representative templates and production-like payloads must be benchmarked.

### Bulk traffic ambiguity

At 5–10 bulk requests/minute and up to 100 documents per batch, the maximum implied bulk arrival rate is 500–1,000 documents/minute. If this is additional to the 1,000 single requests/minute, total demand could be 1,500–2,000 PDFs/minute (25–33.3 PDFs/second). At 2–3 seconds per PDF, that implies roughly 50–100 concurrent render slots and 20–40 GB of renderer memory alone. The product team must clarify whether these figures are additive and whether bulk jobs are expected to complete at maximum batch size at that rate.

### Queue depth and waiting time

The current working model deliberately uses one active renderer and a bounded in-memory waiting queue of 10 requests. This is a local safety mechanism, not a capacity solution. Excess requests are rejected with a controlled overload response rather than allowing unbounded memory growth. A process restart loses the in-memory single-request queue, so the caller must retry or the architecture must move single jobs into a durable queue if lossless acceptance is required.

For bulk work, BullMQ/Redis and PostgreSQL jobs/outbox provide durable coordination. The bulk worker currently uses concurrency 1, which protects memory but means a batch of 100 documents is serialized. If each render truly takes 2–3 seconds, rendering alone takes 200–300 seconds per batch, excluding ZIP creation and overhead. At 5–10 maximum-size batches/minute, one worker cannot keep up; additional isolated worker capacity or a changed traffic/SLO contract is necessary.

### Storage

The problem estimates each PDF at 100 KB–1 MB. Using a planning midpoint of 550 KB:

- 30,000 PDFs/month × 550 KB ≈ 16.5 GB of new PDF data per month.
- With 3 months retained, approximately 49.5 GB of PDF data, before ZIP overhead, manifests, failed attempts, replicas, and backups.
- At the size extremes, monthly new PDF data is approximately 3 GB (100 KB each) to 30 GB (1 MB each).

The archive is a second representation of the PDFs, so storing both individual PDFs and ZIPs can nearly double the storage for the retained period. Retention and cleanup policy materially affect storage cost.

### Network

At 30,000 PDFs/month and 550 KB average, individual PDF payloads alone total about 16.5 GB/month downloaded. ZIP downloads, repeated downloads after interrupted transfers, and manifests add traffic. Range requests can resume a partial download, but they do not reduce the bytes ultimately transferred if the client eventually downloads the full archive.

### What the measurements prove

Observed local results reported during development:

- 100 sequential single-PDF requests: 100/100 successful; 25.62 seconds total; 3.90 successful requests/second; reported first-response p95 293.63 ms.
- After adding a bounded renderer queue: 40/40 successful at concurrency 8; 10.87 seconds total; 3.68 successful requests/second; reported first-response p95 2.27 seconds; zero busy retries.
- Large-document smoke test: 600 line items, HTTP 200, 1,698,657 bytes, 806 ms, valid `%PDF-` header.
- A 100-document bulk batch was reported as completed.

These are development-machine observations, not a production benchmark. The 600-row smoke test validated the PDF header and response size, not that all 600 rows are present in extracted PDF text. The final submission should include the actual archive/signature verification output and recovery-test evidence if those were run. I should not claim those checks passed without their results.

## 4. Design Decisions

### Decision 1: Use a dedicated PDF service instead of embedding rendering inside the ERP request handler

**Alternatives considered:**
- Render PDFs inside the Django monolith.
- Run a separate service dedicated to document rendering.
- Use an external SaaS PDF API.

**Chosen approach:** A separate Fastify/TypeScript service with an HTTP API.

**Why:** Chromium is memory-intensive and can fail on large documents. Isolating it allows the team to set independent resource limits, deploy worker processes separately, and avoid tying up the ERP's web workers while PDFs are generated.

**Tradeoff accepted:** The system adds another deployable service, authentication boundary, network hop, and operational surface. A service boundary is useful only if the team monitors and operates it correctly.

### Decision 2: Use Puppeteer with HTML templates

**Alternatives considered:**
- Generate PDFs directly with a drawing-oriented PDF library.
- Use a commercial/external document-generation API.
- Use Puppeteer to render HTML/CSS.

**Chosen approach:** Puppeteer and HTML/CSS templates.

**Why:** Invoice and purchase-order layouts are naturally expressed in HTML/CSS, and browser rendering provides familiar layout and print styling. It also supports complex tables and long documents.

**Tradeoff accepted:** Chromium is a relatively heavy dependency. Fonts, browser versions, page layout, rendering timeouts, and memory use need testing. HTML templates must escape untrusted data to avoid injection.

### Decision 3: Use PostgreSQL job records plus a transactional outbox

**Alternatives considered:**
- Insert a database row and publish directly to Redis.
- Use Redis as the only job store.
- Persist the job and outbox event in one PostgreSQL transaction, then dispatch to BullMQ.

**Chosen approach:** Store the batch payload and job status in PostgreSQL and create an outbox event in the same transaction. A dispatcher publishes the event to Redis/BullMQ.

**Why:** A direct dual write can commit a database job but fail before queue publication, leaving an accepted job stranded. The outbox makes the intent to publish durable and recoverable.

**Tradeoff accepted:** There is additional dispatcher logic, retry behavior, and operational monitoring. The outbox provides at-least-once publication semantics; idempotent processing is still required. It does not make PostgreSQL and Redis one atomic transaction.

### Decision 4: Bound renderer concurrency and queue length

**Alternatives considered:**
- Allow every incoming request to create a new Chromium page.
- Reject every overlapping request immediately.
- Use a bounded queue and a small number of active renders.

**Chosen approach:** One active render and a bounded waiting queue for the current local model.

**Why:** The supplied 400 MB temporary-memory estimate makes unlimited parallel rendering unsafe. The queue smooths small bursts and gives predictable overload behavior.

**Tradeoff accepted:** Queued requests have higher latency, and a single renderer cannot satisfy the stated peak rate. The in-memory single-request queue is lost on process restart; durable single-job scheduling is a future improvement if the acceptance contract requires it.

### Decision 5: Snapshot the submitted bulk payload

**Alternatives considered:**
- Have the worker query the ERP for every invoice when it is ready to render.
- Persist the full validated JSON payload at batch submission.
- Persist only IDs and depend on versioned source records.

**Chosen approach:** Store the submitted document payloads with the PostgreSQL batch job.

**Why:** The worker renders the same submitted values even if the ERP data changes during a long-running batch. This is the simplest way to make the PDF service's input immutable for that job.

**Tradeoff accepted:** JSON payloads consume database storage and need schema/versioning discipline. The upstream ERP must still construct a consistent batch snapshot; the PDF service cannot fix inconsistent reads that occurred before submission.

### Decision 6: Use a ZIP archive with a signed manifest and resumable downloads

**Alternatives considered:**
- Return PDFs one by one with no archive.
- Produce a ZIP with no integrity information.
- Produce a ZIP with file hashes and a digitally signed manifest.
- Store all artifacts in object storage with pre-signed URLs.

**Chosen approach:** Create a ZIP containing successful PDFs, a manifest with SHA-256 hashes, an Ed25519 signature, and explicit failed-document information. Serve the archive as a stream and support byte ranges.

**Why:** A single archive is convenient for bulk downloads. Range requests let clients resume interrupted downloads, while hashes and a signature make corruption or post-generation file changes detectable.

**Tradeoff accepted:** Signing proves that the manifest was signed by the holder of the private key; it does not prove the business data was correct at creation time, and it does not make storage immutable. The verifier must obtain the trusted public key independently. Local filesystem storage is not suitable for multiple hosts without shared durable storage.

### Decision 7: Use an explicit API key and tenant scope for the working model

**Alternatives considered:**
- Leave endpoints unauthenticated for ease of testing.
- Use a shared internal API key and tenant ID.
- Implement full OAuth2/client credentials or workload identity and fine-grained authorization.

**Chosen approach:** API-key authentication plus tenant-scoped job queries for this project.

**Why:** It is a small, testable service-to-service boundary that demonstrates authentication and tenant isolation without building a full identity provider.

**Tradeoff accepted:** A shared API key is not a full production identity system. Production should use managed secret rotation, stronger workload identity, least privilege, rate limiting, and audited authorization.

## 6. Weaknesses & Future Improvements

### Weakest parts of the current design

1. **Peak capacity is not proven.** The local renderer queue is intentionally conservative. Its observed load-test throughput is well below the stated peak. The project demonstrates admission control and successful local requests, not the ability to sustain 1,000 single requests/minute.
2. **Single-document waiting is in memory.** A process crash can lose requests waiting in the renderer queue. If the contract requires every accepted single request to survive process failure, single jobs should be persisted and dispatched through a durable queue.
3. **The current bulk worker serializes rendering.** One worker with concurrency 1 is memory-safe but cannot complete many maximum-size batches per minute at the assumed 2–3 seconds per render.
4. **Local filesystem storage limits horizontal scaling.** Multiple API/worker instances need shared object storage, access controls, retention policies, and lifecycle cleanup.
5. **Snapshot correctness starts upstream.** Persisting JSON makes the service's input stable, but the ERP must build that JSON from a consistent transaction/snapshot.
6. **Integrity is not immutability.** The signed manifest detects changed content when verified with a trusted public key; it does not prevent an administrator from deleting artifacts or signing a new manifest with the private key.
7. **Observability and operations need more work.** Production needs queue age/depth, render duration, failure rates, memory, browser restarts, storage usage, and alerts. Logs should carry correlation/job IDs without leaking invoice data.
8. **The test evidence is not yet a full production certification.** A successful PDF header check is weaker than verifying all expected content. A completed bulk job should be accompanied by archive listing and manifest-verification output in the submission.

### If I had two more days

- Add an end-to-end script that submits 10 and 100 documents, polls the job, downloads the ZIP, verifies entry counts, and verifies the signed manifest and every PDF hash.
- Add a deterministic PDF-text extraction assertion for a 600-line-item document.

- Add a durable single-job path if single-request acceptance must survive restarts.
- Add a small dashboard or structured metrics for queue depth, queue wait, render duration, PDF failures, memory, and p95 latency.
- Move artifacts behind a storage interface and test an S3-compatible object store if multi-instance deployment is required.

### If load grows 10×

I would not simply increase the renderer concurrency constant. I would:
- Separate synchronous single-document traffic from bulk jobs with independent admission controls and capacity reservations.
- Use durable job acceptance for work that can wait, with priority queues and tenant-level rate limits.
- Run isolated renderer worker processes or containers with measured memory limits and autoscaling based on queue age/depth.
- Load-test representative templates and large documents to find actual render throughput per worker.
- Use shared object storage, lifecycle/retention policies, and signed download URLs or a download gateway.
- Keep PostgreSQL for job metadata and idempotency, tune indexes and connection pools, and avoid holding DB transactions open while publishing to Redis.
- Recalculate capacity from measured render duration and peak arrival rates. If the 400 MB/render assumption remains true, dozens of concurrent renders require substantial memory and likely exceed the original budget.

## 7. One Thing the Problem Statement Didn't Mention

**Operational retention and privacy controls for generated financial documents.**

Invoices and purchase orders can contain customer names, addresses, tax IDs, pricing, and bank or payment details. The service therefore needs a defined retention period, deletion process, encryption at rest, restricted artifact access, and a policy for logs and backups. Without this, a technically correct PDF service can retain sensitive files indefinitely or expose them through overly broad storage permissions.

The signed manifest is useful for integrity, but it is not an access-control mechanism. The API's tenant checks, storage permissions, key management, and deletion policy must protect confidentiality and lifecycle as well as tamper evidence.

A related production concern is template safety: untrusted fields must be escaped, external resource loading should be restricted, and Chromium should run with appropriate sandboxing and process/container limits.

### Budget conclusion and recommended approach

The budget, peak throughput, and 400 MB/render memory assumption are in tension. A small low-volume demo deployment can be cheaper, but it must not be represented as proven to support the peak workload.

For a portfolio/demo environment, the most economical approach is to use the existing shared ERP infrastructure only if its resource headroom is measured and the PDF renderer cannot destabilize the ERP. Otherwise, use a small isolated test environment and document that the production peak needs a separate capacity and cost plan.

For the stated peak, first clarify whether bulk document rates are additional to single requests. Then benchmark representative documents and calculate the number of isolated render slots.
